# 관리자 히스토리 로그 뷰어 설계

## 책임과 승인 기준

관리자 영역의 책임은 **전체 계산 이력을 읽기 전용으로 확인하는 히스토리 로그 뷰어**다. 운영 대시보드, 설정 도구, 시스템 제어 콘솔로 확장하지 않는다.

승인 기준은 다음과 같다.

- 관리자 진입 후 최신순 계산 히스토리를 바로 연다.
- 기간, 세션 ID, 상품명, 최종 상태로 기록을 찾는다.
- 각 행에서 시각, 상태, 상품 요약, 수량, 금액, 특이사항을 확인한다.
- 한 번의 행 선택으로 계산 상세를 연다.
- 상세에서 촬영부터 최종 결과까지 저장된 사실을 시간순으로 확인한다.
- AI 원판정, 고객 선택, 최종 결제 결과를 서로 다른 사실로 표시한다.
- `Unknown`은 등록 SKU와 구분하고 등록 SKU 합계에 포함하지 않는다.
- 관리자 화면에서 어떤 원본 기록도 수정하지 않는다.

## 관리자 영역의 존재 의미

고객 또는 직원이 지난 계산을 다시 확인해야 할 때 저장된 사실을 읽기 쉬운 순서로 보여준다.

- 언제 계산했는가?
- 어떤 사진과 객체가 기록되었는가?
- AI는 각 객체를 어떤 SKU 또는 `Unknown`으로 판단했는가?
- 고객이 결과를 그대로 사용했는가, 다른 상품을 선택했는가?
- 최종 주문과 결제 결과는 무엇인가?
- 재촬영, 오류, 취소 또는 중단이 있었는가?

문제 기록만 모으는 검토함이 아니라 모든 계산 기록을 다룬다. 특이사항은 기록을 찾기 쉽게 표시할 뿐, 새로운 오류 판정을 만들지 않는다.

## 범위

### 포함

- 전체 계산 세션 히스토리
- 최신순 목록과 날짜 구분
- 기간, 세션 ID, 상품명, 최종 상태 검색 및 필터
- 완료, 취소, 실패, 중단 상태
- `Unknown`, 고객 수정, 재촬영, 수량 불일치, 오류 표시
- 계산 상세의 시간순 이벤트
- 보존된 촬영 이미지와 canonical 객체 박스
- AI 원판정, Top-3 후보, 고객 선택, 최종 결제 상품
- 접힌 기술 정보 영역의 provenance

### 제외

- 운영 KPI 대시보드
- 관리자 검토 작성
- 상품과 가격 관리
- 고객 화면과 카메라 설정
- 모델, 임계값, 융합 정책 또는 아티팩트 변경
- 시스템 재시작, 복구 또는 원격 제어
- 사용자 계정과 권한 체계
- 다점포 관제, 클라우드 동기화와 백업
- 고객 행동을 이용한 실시간 정확도 계산

기존 상품 관리, 설정, 진단, 검토 구현은 이 설계에서 삭제하지 않는다. 관리자 기본 탐색에서만 제외하며 후속 정리는 별도 변경으로 결정한다.

## 정보 구조

관리자 진입 후 별도 대시보드를 거치지 않고 히스토리 목록을 바로 연다.

```text
고객 화면
  -> 관리자/히스토리 진입
  -> 계산 히스토리 목록
       -> 계산 상세
            -> 기술 정보 펼치기
```

관리자 셸의 주 목적지는 `히스토리` 하나다. 상세에서 돌아오면 기존 필터와 스크롤 위치를 복원한다.

## 히스토리 목록

### 기본 표시

계산 세션 한 건을 한 행으로 표시하고 최신순으로 정렬한다. 날짜가 바뀌는 지점에는 날짜 구분선을 둔다.

각 행은 다음 정보를 표시한다.

- 계산 또는 세션 시작 시각
- 세션 ID 축약값
- 최종 상태
- 대표 상품명과 나머지 상품 종류 수
- 최종 결제 수량
- 최종 결제 금액
- 특이사항 배지

상품 요약은 `크루아상 2개 외 1종`처럼 표시한다. 결제 결과가 없는 기록은 없는 값을 `0원`이나 `0개`로 만들지 않고 `미확정`으로 표시한다.

### 상태와 특이사항

최종 상태는 `완료`, `취소`, `실패`, `중단`, `진행 중`으로 표시한다.

특이사항은 저장된 사실에서만 파생한다.

- `AI 미확정`: 하나 이상의 객체 원판정이 `Unknown`
- `고객 수정`: 고객 선택이 AI 자동 결과와 다름
- `재촬영`: 둘 이상의 촬영 시도 존재
- `수량 불일치`: 검출 객체 수와 고객 확인 수량이 다름
- `오류`: 카메라, 추론, 저장 또는 결제 오류 존재

배지는 정확도나 오류 확정 판정이 아니라 사건이 있었다는 사실만 표현한다.

### 검색과 필터

상단 도구는 다음으로 제한한다.

- 오늘, 최근 7일, 최근 30일
- 사용자 지정 기간
- 세션 ID 검색
- 상품명 검색
- 최종 상태
- 특이사항 있는 기록만 보기

필터를 변경하면 목록을 처음부터 다시 불러온다. 추가 로딩 실패는 기존 목록을 유지한 채 재시도한다.

## 히스토리 상세

### 결과 요약

상단에서 최종 상태와 시각, 상품별 수량과 가격, 총수량과 총금액, 촬영 횟수, 특이사항, 전체 세션 ID를 먼저 보여준다. 결제되지 않은 세션은 결제 결과가 없는 이유를 상태와 함께 표시한다.

### 시간순 로그

저장된 사건을 다음 순서로 배열한다.

1. 세션 시작
2. 촬영 시도
3. AI 분석 결과
4. 고객 확인 또는 수정
5. 주문 확정
6. 결제 완료, 취소, 실패 또는 중단

실제 저장 시각과 출처를 사용하며, 저장되지 않은 중간 상태를 추정해 만들지 않는다.

### 촬영 및 객체 확인

보존된 원본 이미지를 canonical orientation으로 표시하고 canonical 박스를 같은 좌표계에 겹친다. 이미지나 박스를 확인할 수 없으면 대체 자료를 만들지 않고 누락 또는 무결성 실패를 표시한다.

객체를 선택하면 다음 사실을 구분해 표시한다.

- 객체 ID와 canonical box
- AI 원판정 SKU 또는 `Unknown`
- 저장된 Top-3 후보와 순서
- 고객 선택 상품과 선택 출처
- 최종 주문 상품
- 결정 경로와 신뢰도

AI 원판정, 고객 선택, 최종 주문은 서로 덮어쓰지 않고 나란히 비교한다.

### 기술 정보

모델과 증적 정보는 기본적으로 접는다.

- detector, RepViT, DINOv3, fusion artifact ID
- SHA-256과 무결성 상태
- 정책, 전처리, 카탈로그, 설정 리비전
- detector threshold 출처
- 장치와 단계별 실행 시간

저장된 provenance만 표시하고 수정 버튼은 제공하지 않는다.

## 데이터와 불변성

히스토리는 세션, 스캔 시도, 추론, 고객 선택, 주문, 결제의 읽기 전용 projection이다.

- 추론 영수증, 고객 선택, 주문과 결제를 수정하지 않는다.
- 별도의 관리자 판정 또는 교정 데이터를 만들지 않는다.
- 등록 SKU별 수량은 등록된 최종 객체만 센다.
- `Unknown` 수량은 별도로 유지한다.
- 이미지와 영수증 및 구성 증적의 SHA-256을 검증한다.
- 누락되거나 손상된 증적을 정상으로 표시하지 않는다.

## 로딩과 오류 처리

- 최초 목록 실패는 빈 목록과 구분하고 재시도를 제공한다.
- 추가 목록 실패는 이미 불러온 기록을 지우지 않는다.
- 상세 실패는 같은 세션을 다시 시도할 수 있게 한다.
- 이미지 실패는 나머지 텍스트 기록을 계속 보여준다.
- 누락된 사건을 추정해 채우지 않는다.
- 서로 모순된 데이터는 임의로 하나를 선택하지 않고 불일치를 표시한다.

## 화면 원칙

- 목록은 빠르게 훑을 수 있는 조밀한 행 구조를 사용한다.
- 상태와 특이사항은 색상뿐 아니라 텍스트로 구분한다.
- 상세는 내부 테이블 순서가 아니라 사건 순서로 구성한다.
- AI 원판정과 최종 결제 결과의 차이를 한 화면에서 확인할 수 있어야 한다.
- 모델명, 해시, raw JSON은 기본 정보보다 앞서지 않는다.
- 수정, 저장, 검토 완료 또는 재처리 버튼을 제공하지 않는다.
- 1280×820과 1024×720에서 키보드와 터치로 접근할 수 있어야 한다.

## 기존 구현과의 관계

기존 `TransactionHistoryScreen`의 검색, 필터, 페이지 로딩과 상세 진입 계약을 재사용한다. `TransactionDetailScreen`의 거래, 세션, 이미지, 추론, 주문, 결제와 provenance 데이터를 시간순 표현으로 재구성한다.

`DashboardScreen`, `ReviewInboxScreen`, `ProductManagementScreen`, `DiagnosticsScreen`, `SettingsScreen`은 새 관리자 기본 흐름에 포함하지 않는다. 이 설계만으로 기존 파일이나 저장 데이터를 삭제하지 않는다.

## 검증

### 계약

- 목록의 상태, 수량, 금액이 최종 주문과 결제 기록과 일치한다.
- AI 원판정, 고객 선택, 최종 주문이 각각 원본 출처와 일치한다.
- `Unknown`이 등록 SKU 합계에 포함되지 않는다.
- 목록 행과 상세가 같은 세션을 참조한다.
- 관리자 화면에서 원본 기록에 쓰기가 발생하지 않는다.

### 사용자 흐름

- 최신 계산이 목록 첫머리에 나타난다.
- 기간, 세션 ID, 상품명, 상태와 특이사항 필터가 기록을 찾는다.
- 한 번의 행 선택으로 상세를 연다.
- 상세에서 돌아오면 목록 상태가 유지된다.
- 완료, 고객 수정, `Unknown`, 재촬영, 실패와 중단 기록을 확인할 수 있다.

### 실패와 접근성

- 목록, 다음 페이지, 상세와 이미지 실패가 각각 복구 가능한 상태로 보인다.
- 손상된 증적은 정상 자료처럼 표시되지 않는다.
- 키보드 포커스, 터치 영역, Windows 텍스트 배율과 스크린리더 레이블을 검증한다.
- 1280×820 및 1024×720에서 오버플로가 없어야 한다.

### 회귀 경계

- canonical RF-DETR-L, RepViT, conditional DINOv3, fusion 및 `Unknown` 계약을 변경하지 않는다.
- 고객 체크아웃, 결제 내구성, 카탈로그 리비전과 감사 저장을 변경하지 않는다.
- `portable_cpu_smoke/`와 legacy pipeline 동작을 변경하지 않는다.
- 사용할 수 없는 검증은 통과가 아니라 미검증으로 보고한다.

## 구현 우선순위

1. 관리자 진입 기본 목적지를 히스토리 목록으로 변경한다.
2. 목록 행을 날짜, 상품, 수량, 금액, 상태와 특이사항 중심으로 재구성한다.
3. 검색과 필터를 최소화하고 목록 상태를 복원한다.
4. 상세 화면을 결과 요약과 시간순 로그로 재구성한다.
5. 보존 이미지, canonical 박스와 객체별 판정을 연결한다.
6. provenance를 접힌 기술 정보로 이동한다.
7. 기존 관리자 쓰기 화면을 기본 탐색에서 제외하고 회귀 검증한다.

## 완료 기준

- 모든 계산 히스토리가 최신순으로 조회된다.
- 필요한 기록을 검색과 필터로 찾을 수 있다.
- 한 번의 선택으로 상세에 진입한다.
- 상세에서 촬영부터 최종 결과까지 저장된 사건을 순서대로 확인한다.
- AI 원판정, 고객 선택, 최종 결제 상품이 명확히 구분된다.
- `Unknown`, 등록 SKU 수량, 최종 주문 수량과 금액이 원본과 일치한다.
- 관리자 화면에서 원본 또는 파생 운영 데이터를 수정하지 않는다.
- 관련 계약, UI, 통합, 접근성 및 회귀 검증 결과를 기록한다.
