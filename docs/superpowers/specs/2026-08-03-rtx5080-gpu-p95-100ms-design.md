# RTX 5080 GPU 추론 p95 100ms 설계

**상태:** 2026-08-03 사용자 승인, 구현 전 설계 기준선

**대상 브랜치:** `codex/gpu-p95-100ms`

**책임:** 정식 판정 의미와 실패 폐쇄 동작을 보존하면서 선택 가능한 GPU 실행 경로와 그 성능 증거를 제공한다.

## 1. 목표와 측정 경계

현재 RTX 5080에서 단일 스캔 이미지(`batch=1`)의 warmed worker end-to-end 지연시간을 다음 조건으로 낮춘다.

- E, M, H 각 난이도 그룹의 p95가 모두 `100ms` 이하이다.
- 세 그룹을 합친 전체 p95도 `100ms` 이하이다.
- 타이머는 worker가 입력 파일의 바이트를 읽기 직전에 시작한다.
- 타이머는 최종 객체 목록, SKU별 합계, 별도 `Unknown` 합계, Unknown별 Top5 후보와 provenance를 포함한 결과 payload가 메모리에 완성될 때 끝난다.
- 파일 읽기, EXIF 해석과 canonical RGB 변환, 검출, crop 생성, RepViT, 조건부 DINOv3, fusion, 집계와 payload 조립을 포함한다.
- 카메라 촬영, Flutter/IPC 왕복, UI 렌더링은 포함하지 않는다.
- 모델 및 engine 로드와 최초 warm-up은 포함하지 않지만 그 시간은 별도 보고한다.

`100ms`는 품질을 낮춰 달성하는 목표가 아니다. 품질 또는 provenance gate를 충족하지 못한 후보는 빠르더라도 채택하지 않는다.

## 2. 현재 기준선과 해석 한계

커밋된 `benchmarks/baselines/flutter_camera_prototype_20260729/warm_benchmark.json`의 warmed CUDA 실행 결과는 다음과 같다.

| 구간 | p50 | p95 |
| --- | ---: | ---: |
| decode/preprocess | 76.20ms | 98.68ms |
| RF-DETR-L | 99.41ms | 123.70ms |
| RepViT-M1 | 62.82ms | 80.00ms |
| 조건부 DINOv3 | 73.31ms | 90.40ms |
| postprocess | 0.34ms | 0.38ms |
| 합계 | 368.68ms | 419.20ms |

이 결과는 RTX 5080, `cuda:0`, 3개 객체가 검출되는 단일 이미지, 20회 측정의 prototype 기준선이다. 목표까지 약 `4.2x`의 p95 개선이 필요하고 검출기 p95만으로도 목표를 넘는다. 따라서 Python loop 제거만으로는 충분하지 않다.

이 기준선은 현재 병목 위치를 찾는 개발 증거일 뿐 최종 수락 증거가 아니다. 이미지 한 장과 20회 측정만으로 E/M/H 전체 성능이나 정확도를 대표한다고 주장하지 않는다.

## 3. 보존해야 하는 판정 계약

GPU 경로는 `configs/pipelines/canonical_cpu.yaml`의 의미론적 계약을 바꾸지 않는다.

1. EXIF transpose를 적용한 RGB 이미지가 유일한 canonical coordinate frame이다.
2. RF-DETR-L은 `models/rfdetr_large_bakery_v1/manifest.json`의 calibrated threshold를 사용한다.
3. box는 canonical frame의 유한하고 유효한 `[x_min, y_min, x_max, y_max]`로 정규화한다.
4. 모든 검출 후보는 detector artifact ID, calibrated score와 provenance를 유지한다.
5. 모든 accepted crop에 `repvit_m1_15plus5_v1`을 실행한다.
6. immutable calibrated RepViT gate가 수락한 direct decision만 최종 판정이 된다.
7. direct-gate reject에만 `dinov3_vits16_15plus5_v1`의 global/local evidence를 실행한다.
8. immutable fusion의 ranked SKU가 local Top-1과 같거나, 두 모델의 global Top-1이 ranked SKU와 같고 fusion margin이 `0.85` 이상일 때만 등록 SKU를 수락한다.
9. 나머지는 모두 `Unknown`이며 임의 SKU로 대체하거나 SKU별 합계에 넣지 않는다. 각 Unknown에는 사용자 확인용 ranked Top5를 보존하되 후보 자체는 판정이 아니다.
10. 모든 모델, preprocessing, calibration, prototype/support bank, policy의 SHA-256을 실행 전에 검증한다.

GPU 최적화는 실행 방식만 바꾼다. threshold, gate, fusion 수식, candidate 순서, tie-break, `Unknown` 의미는 바꾸지 않는다. canonical CPU/FP32 composition은 참조 구현이자 안전한 운영 경로로 남는다.

## 4. 검토한 접근과 선택

### 접근 A: 현재 PyTorch eager 경로만 배치화

객체별 `classifier.infer()` 호출을 `infer_many()`으로 바꾸고 PIL crop 및 `.item()`/`.cpu()` 동기화를 줄인다. 위험과 구현 비용이 가장 낮고 반드시 먼저 해야 하지만, 검출기 p95가 이미 123.70ms라서 단독으로 100ms를 보장할 수 없다.

### 접근 B: 동일 모델·동일 판정의 정적 GPU 실행 경로

객체 배치화에 더해 tensor 기반 crop/preprocess, RF-DETR-L 및 분류 backbone의 TensorRT FP16 engine, 고정/제한된 shape profile, 사전 할당 buffer, CUDA Graph를 사용한다. 민감한 score, gate 및 fusion 연산은 필요하면 FP32로 유지한다. 속도와 품질 위험의 균형이 가장 좋아 기본 설계로 선택한다.

### 접근 C: FP8/INT8/FP4 또는 더 작은 detector

Blackwell에서 큰 추가 가속 여지가 있지만 calibration과 수치 변화 또는 모델 품질 변화가 생긴다. 접근 B가 증거 기반으로 목표를 달성하지 못할 때만 별도 실험으로 연다. 기존 locked set을 보고 precision, threshold 또는 모델을 선택하지 않으며 새 calibration 및 새 locked acceptance set 없이 production에 채택하지 않는다.

## 5. 목표 아키텍처

```text
input path
  -> encoded bytes + EXIF metadata
  -> CanonicalInputAdapter
       -> EXIF-transposed RGB canonical frame
       -> canonical tensor + exact image/transform provenance
  -> GpuRuntimeAdmission
       -> artifact hashes / engine compatibility / runtime identity 검증
  -> RfDetrGpuAdapter
       -> manifest threshold
       -> canonical boxes + detector evidence
  -> GpuCropBatchBuilder
       -> 모든 accepted object의 RepViT view batch
  -> RepVitGpuBatchScorer
       -> immutable direct gate
       -> accepted decisions + rejected object indices
  -> conditional DinoGpuBatchScorer
       -> rejected object의 global/local view batch만 실행
  -> ImmutableDecisionAssembler
       -> 기존 fusion policy와 Unknown 처리
       -> totals + Unknown Top5 + provenance + result payload
```

### 5.1 `CanonicalInputAdapter`

- 현재 PIL/EXIF 경로를 reference adapter로 유지한다.
- optimized adapter는 encoded bytes를 한 번 읽고 EXIF orientation을 명시적으로 해석한다.
- GPU JPEG decode를 사용한다면 orientation을 별도로 정확히 적용한다. `torchvision.io.decode_jpeg(..., device="cuda")`는 nvJPEG를 사용할 수 있지만 `apply_exif_orientation`은 CPU에서만 지원되고, NVIDIA DALI JPEG decoder는 EXIF orientation을 무시하므로 암묵적 동작에 의존하지 않는다.
- 8개 EXIF orientation과 RGB 변환을 포함한 pixel/geometry contract test를 통과해야 한다.
- optimized pixel 결과가 reference와 동일하지 않은 codec edge case는 최종 판정 및 box parity까지 검증한다. parity를 증명하지 못한 입력은 명시적으로 reference adapter로 보내며 그 사실과 시간이 receipt에 기록된다.

### 5.2 `GpuRuntimeAdmission`

- 실행 전에 source model, preprocessing, policy와 engine artifact의 identity 및 SHA-256을 모두 검증한다.
- engine의 GPU compute capability, TensorRT/CUDA/runtime version, precision, input/output binding, shape profile이 현재 환경과 맞는지 검증한다.
- benchmark에서는 fallback을 금지한다. admission 실패는 해당 실행을 `unverified`로 종료한다.
- production에서는 구성으로 명시된 canonical CPU fallback만 허용하고 fallback reason을 결과와 운영 로그에 기록한다. fallback 실행을 GPU 성능 표본으로 집계하지 않는다.

### 5.3 `RfDetrGpuAdapter`

- high-level `predict()` 호출 대신 검증된 export graph의 입력과 출력을 직접 관리한다.
- detector 입력 해상도는 코드에 새로 하드코딩하지 않고 source artifact/export metadata에서 해석해 engine manifest에 고정한다.
- 첫 production 후보는 batch-1 TensorRT FP16이다.
- resize/normalize, detector inference, decode/NMS가 GPU resident 상태를 유지하도록 하고 최종 canonical box/evidence에 필요한 최소 데이터만 복사한다.
- threshold 적용, box clip/order, score tie-break는 reference와 동일해야 한다.

### 5.4 `GpuCropBatchBuilder`와 분류기

- 현재 객체별 Python 호출을 제거하고 한 이미지의 모든 후보를 안정적인 detector order로 모은다.
- RepViT에 필요한 global/local view를 GPU tensor operation으로 한 번에 생성한다.
- RepViT 결과에서 direct-gate reject index를 GPU에서 만들고 DINOv3에는 해당 객체의 global/local evidence만 packed batch로 전달한다.
- 최종 객체 순서는 detector order로 복원한다. batch padding은 판정 evidence나 합계에 포함하지 않는다.
- common object-count shape에는 사전 할당 buffer와 CUDA Graph를 사용하고, 지원 범위 전체를 처리하는 검증된 dynamic profile도 유지한다. 후보를 버리거나 임의 최대 개수에서 잘라내지 않는다.
- DINO 실행률, 객체 수, 선택한 profile을 표본마다 기록한다.

### 5.5 `ImmutableDecisionAssembler`

- 기존 calibrated RepViT gate, fusion policy, margin 비교와 `Unknown` 집계를 재사용한다.
- GPU adapter는 raw evidence와 provenance를 생산하고 판정 policy를 소유하지 않는다.
- host sync는 payload 생성 직전 한 번으로 모으되, 그 결과가 기존 안정적 순서와 tie-break를 바꾸지 않아야 한다.

### 5.6 `LatencyRecorder`

- end-to-end gate는 host monotonic clock으로 측정한다.
- GPU stage 진단은 CUDA Event와 NVTX range를 사용한다.
- 각 stage 경계에서 `torch.cuda.synchronize()`를 호출해 pipeline을 직렬화하지 않는다. 측정 반복이 끝날 때 event를 회수하기 위한 제한된 동기화만 한다.
- stage p95의 합을 total p95로 사용하지 않는다. 표본별 실제 total을 집계한다.

## 6. 정밀도와 parity 전략

단계를 한 번에 섞지 않아 회귀 원인을 분리한다.

1. **Batch FP32:** 현재 모델과 preprocessing을 유지하고 객체 배치 및 동기화 제거 효과를 측정한다.
2. **Tensor preprocess FP32:** PIL 기반 다중 crop을 GPU tensor path로 바꾸고 canonical/crop parity를 확인한다.
3. **TensorRT FP16 detector:** RF-DETR-L backbone/graph를 FP16으로 실행하되 score decode와 threshold 경계는 필요한 경우 FP32로 올린다.
4. **TensorRT FP16 classifiers:** RepViT/DINO feature extraction을 FP16으로 실행하되 prototype similarity, calibrated gate 및 fusion 입력은 민감도 분석에 따라 FP32로 유지한다.
5. **CUDA Graph/buffer reuse:** 수치 경로가 고정된 뒤 graph capture를 적용한다.

각 단계는 직전 단계와 독립적으로 benchmark/quality receipt를 만든다. FP16 변환으로 final decision parity가 깨지면 layer별 mixed precision을 사용해 원인을 격리한다. 그래도 parity를 복구하지 못하면 해당 backend는 새로운 calibrated backend로 취급하고 개발/보정/새 locked acceptance evidence를 분리한다. 기존 threshold나 gate를 속도 목표에 맞춰 완화하지 않는다.

## 7. 계획 지연시간 예산

다음 값은 구현 우선순위를 정하기 위한 p95 상한 예산이며 측정 결과가 아니다.

| 구간 | p95 예산 |
| --- | ---: |
| 파일 읽기 + canonical decode/EXIF/RGB | 12ms |
| RF-DETR-L + box decode | 35ms |
| GPU crop + RepViT batch + direct gate | 15ms |
| 조건부 DINOv3 batch | 22ms |
| fusion + copy + aggregation + payload | 4ms |
| 변동 여유 | 12ms |
| 합계 | 100ms |

예산을 넘는 stage는 정확도 우회가 아니라 profile, memory transfer, kernel coverage, graph break와 host sync를 먼저 조사한다. 조건부 DINO 비율이 높은 H 그룹도 독립 p95 gate를 통과해야 한다.

## 8. 성능 측정 프로토콜

### 8.1 표본과 실행

- 모델, engine, calibration, policy, preprocessing, 데이터 manifest, seed와 code commit을 고정한다.
- 고정 E/M/H performance manifest를 사용하고 그룹별 최소 100개 유효 total latency 관측치를 만든다.
- 최소 20회 warm-up 후 측정하며 warm-up 표본은 통계에서 제외한다.
- 반복 순서와 cache 효과가 한 후보에 유리하지 않도록 reference/candidate를 교차 실행한다.
- candidate와 reference를 동시에 GPU에서 실행하지 않는다.
- GPU persistence/power mode, clock, 온도, 전력, background process, driver, CUDA, cuDNN, TensorRT, PyTorch version을 receipt에 기록한다.
- engine build는 측정 밖에서 수행하며 build time과 warm-up time은 별도 보고한다.

### 8.2 필수 보고값

- 전체와 E/M/H별 p50, p90, p95, p99, max, sample count
- decode, detector, crop, RepViT, DINO, fusion/copy/payload의 표본별 stage 통계
- 이미지별 accepted object 수와 조건부 DINO 실행 객체 수/비율
- 선택된 shape profile, fallback 여부와 reason
- CPU/GPU memory peak, engine load time, warm-up time
- reference 대비 absolute latency 및 speedup

### 8.3 성능 수락 조건

- E p95 `<=100ms`
- M p95 `<=100ms`
- H p95 `<=100ms`
- 전체 p95 `<=100ms`
- 모든 표본이 검증된 GPU 경로를 사용하고 silent fallback이 0건이다.
- committed performance receipt가 없으면 속도 개선을 주장하지 않는다.

## 9. 품질 및 실패 폐쇄 수락 조건

성능 개발용 데이터, calibration 데이터, locked acceptance 데이터는 서로 분리한다. locked 결과가 precision, profile 또는 구현 선택에 영향을 주면 새 locked set에서 다시 검증한다.

reference와 candidate를 canonical frame IoU `0.50`의 deterministic one-to-one matching으로 비교하고 다음을 모두 보고한다.

- SKU 오류, miss, duplicate, non-target detection, split, merge
- registered SKU 및 `Unknown`별 final-versus-ground-truth count
- direct, DINO-local, global-consensus, `Unknown` decision path 분포
- detector box/score, RepViT score/gate, DINO global/local score, fusion rank/margin의 경계 사례

production 채택 조건은 다음과 같다.

- 새 잘못된 등록 SKU가 0건이다.
- 새 miss, duplicate, non-target, split, merge가 0건이다.
- reference에서 정확했던 객체의 SKU가 candidate에서 다른 등록 SKU로 바뀌지 않는다.
- ambiguity로 인한 차이는 임의 SKU가 아니라 `Unknown`으로 실패 폐쇄된다.
- `Unknown`은 SKU별 합계에 포함되지 않고 별도 집계된다.
- 최신 committed canonical reference receipt의 품질 floor를 모두 유지한다. 기존 CPU 최적화 문서의 `Top-1 >=1349/1406`, `Top-3 >=1390/1406`, `FP=0`, `FN<=5`, `Unknown<=48`, `A-to-B<=4`보다 낮은 floor를 선택할 수 없다. 실행 시 더 최신이고 더 엄격한 canonical receipt가 있으면 그 receipt와 hash를 기준으로 한다.
- final fields의 SKU/count/location/confidence/path와 provenance가 서로 일치한다.

수치 backend가 final parity를 깨는 경우, 정확도 aggregate가 우연히 같더라도 원인을 설명하고 새 calibration/locked evidence를 만들기 전에는 채택하지 않는다.

## 10. Artifact 및 provenance 계약

ONNX와 TensorRT engine은 대용량 외부 artifact로 취급한다. Git에는 engine payload를 넣지 않고 작은 manifest, lock entry, build recipe와 compact receipt만 둔다.

각 engine manifest에는 최소한 다음이 포함된다.

- engine ID, byte size, SHA-256, storage class, expected local path
- source model/checkpoint ID와 SHA-256
- exporter code commit, export command/recipe, opset와 exporter/runtime versions
- preprocessing ID/hash 및 input color/order/layout/range
- dynamic/static shape profile과 detector resolution의 출처
- precision과 layer별 override, calibration ID/hash(해당 시)
- input/output binding name, dtype, shape, semantic meaning
- TensorRT/CUDA/cuDNN version, GPU architecture/compute capability
- build 환경과 build receipt hash

결과 payload는 기존 모델/calibration/policy provenance에 선택된 engine/profile/runtime identity를 추가한다. 결과를 재현하기에 필요한 항목이 없으면 실행을 거부한다.

## 11. 테스트 전략

### 11.1 단위 및 contract 테스트

- 8개 EXIF orientation, RGB 변환, canonical dimensions와 pixel/box mapping
- finite/in-bounds box normalization과 stable order/tie-break
- 다양한 객체 수에서 GPU crop batch와 reference crop의 좌표/내용 parity
- batch padding/packing/unpacking 후 객체 순서 및 decision path 보존
- direct-gate reject에만 DINO가 실행되는지 검증
- local Top-1/global consensus/margin `0.85` 경계와 `Unknown` 처리
- registered/Unknown 합계 불변식
- engine binding, artifact hash, runtime compatibility admission
- admission 실패 및 benchmark fallback 금지
- provenance completeness와 receipt schema

### 11.2 통합 및 GPU 테스트

- reference FP32와 각 최적화 단계의 raw evidence/final decision 비교
- 실제 RTX 5080에서 TensorRT engine load, warm-up, shape profile, CUDA Graph replay
- mixed object count와 DINO 조건 분기
- corrupted/missing engine, hash mismatch, unsupported runtime의 fail-closed 동작
- canonical CPU 경로와 legacy `portable_cpu_smoke/` 무변경 회귀 확인

### 11.3 성능 및 locked acceptance

- 고정 E/M/H latency suite와 전체 manifest suite
- 새 locked quality suite에서 one-to-one IoU 0.50 평가
- skipped 또는 artifact 부재 suite는 `unverified`로 기록하며 passed로 간주하지 않는다.

## 12. 단계별 전달과 중단 조건

1. **Benchmark 신뢰성:** 측정 경계, CUDA Event recorder, E/M/H manifest, receipt schema를 먼저 고정한다.
2. **Batch FP32:** `camera_runtime`의 객체별 호출을 classifier batch contract로 교체하고 증거를 만든다.
3. **Tensor crop/preprocess:** canonical 및 crop parity를 확보한다.
4. **RF-DETR TensorRT FP16:** detector adapter/engine/artifact admission을 추가한다.
5. **RepViT/DINO TensorRT FP16:** 조건부 packed batch 및 mixed precision을 추가한다.
6. **CUDA Graph 및 buffer reuse:** 검증된 shape에만 적용한다.
7. **수락:** performance receipt와 새 locked quality receipt가 모두 통과한 후보만 production opt-in 모드로 올린다.
8. **조건부 연구:** 100ms가 미달일 때에만 FP8/INT8/FP4 또는 detector 교체를 별도 설계·보정·수락 작업으로 연다.

각 단계는 실패하는 테스트를 먼저 식별하고 가장 작은 producer/consumer surface를 함께 변경한다. 단계가 품질 gate를 깨면 다음 최적화를 쌓지 않고 해당 단계에서 중단해 원인을 해결하거나 되돌린다.

## 13. 운영 모드와 롤백

실행 모드는 명시적으로 구분한다.

- `cpu_canonical_fp32`: 현재 canonical/reference
- `gpu_reference_fp32`: 수치 비교용 GPU reference
- `gpu_batch_fp32`: 배치 및 sync 최적화 단계
- `gpu_trt_fp16`: production 후보
- `gpu_quantized_experimental`: 별도 보정 전에는 production 금지

기본 canonical CPU config를 GPU로 조용히 바꾸지 않는다. GPU 후보는 opt-in으로 배포하고 receipt가 지정한 환경과 artifact에만 admission된다. 이상 시 last-known-validated mode로 명시적 롤백하며 rollback reason과 실행 mode를 결과에 남긴다.

## 14. 범위 밖

- canonical CPU 모델 또는 판정 정책 교체
- camera capture, Flutter IPC, UI render의 지연시간을 100ms worker gate에 포함하는 작업. `Top5 + 전체 상품 검색` 사용자 확인 동작 자체는 별도 승인 설계에서 구현한다.
- 새 SKU 학습이나 데이터 라벨 정책 변경
- 정확도 증거 없는 quantization 또는 작은 detector의 production 채택
- `portable_cpu_smoke/` 또는 legacy GPU 경로 삭제·이동·행동 변경
- private/proprietary dataset, checkpoint 또는 engine payload의 Git 커밋

## 15. 완료 조건

이 작업은 다음 조건을 모두 충족할 때 완료된다.

1. 위 아키텍처와 runtime mode가 구현되고 canonical/legacy 계약 테스트가 통과한다.
2. 모든 artifact와 runtime admission이 hash 및 compatibility를 검증한다.
3. RTX 5080에서 E/M/H와 전체 warmed worker p95가 각각 100ms 이하인 committed receipt가 있다.
4. 새 locked set의 품질 gate가 통과하고 오류/Unknown/count/path/provenance 보고가 완전하다.
5. configs, docs, runtime payload와 compact benchmark summary가 실제 동작과 일치한다.
6. 사용할 수 없거나 skipped된 필수 suite가 하나라도 있으면 완료가 아니라 `unverified`로 남는다.
