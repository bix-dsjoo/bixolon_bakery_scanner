# RTX 5080 p95 100ms + Top3 사용자 확인 통합 설계

**상태:** 2026-08-03 사용자 승인, 구현 전 통합 설계 기준선

**대상 브랜치:** `codex/gpu-p95-100ms`

**책임:** canonical 자동 판정 의미와 실패 폐쇄 동작을 보존하면서 RTX 5080 warmed worker p95를 100ms 이하로 낮추고, 자동 확정이 불가능한 객체를 immutable `Unknown + Top3`와 전체 상품 검색으로 안전하게 사용자 확인한다.

## 1. 최종 목표

정상 촬영된 단일 스캔 이미지(`batch=1`)에 대해 다음을 모두 만족한다.

- E, M, H 각 난이도 그룹의 warmed worker p95가 각각 `100ms` 이하이다.
- 세 그룹을 합친 전체 warmed worker p95도 `100ms` 이하이다.
- 자동으로 잘못 확정한 등록 SKU가 0건이다.
- 검출 또는 촬영 배치가 부적합하면 분류를 강행하지 않고 재배치·재촬영을 요청한다.
- 자동 판정이 수락하지 않은 객체는 `Unknown + Top3`로 남는다.
- 사용자는 Top3 중 하나를 선택하거나 전체 활성 상품 catalog를 검색해 선택할 수 있다.
- 사용자 선택은 원본 inference receipt를 수정하지 않고 별도의 audited resolution로 저장한다.

`100ms`는 품질을 낮춰 달성하는 목표가 아니다. 속도 또는 사용자 편의를 이유로 detector threshold, RepViT gate, DINO/fusion 수락 조건이나 `Unknown` 의미를 완화하지 않는다.

## 2. 통합 데이터 흐름

```text
input path
  -> encoded bytes + EXIF metadata
  -> EXIF-transposed RGB canonical frame
  -> RF-DETR-L
  -> scene presentation gate
       -> no object / calibrated overlap: needs_retake
       -> usable scene: ordered canonical boxes
  -> all-object GPU batch crop
  -> RepViT-M1 batch scoring + immutable direct gate
       -> accepted: registered SKU
       -> rejected indexes only: conditional DINOv3 global + local batch
  -> immutable fusion consensus
       -> accepted: registered SKU
       -> rejected: Unknown + exact ranked Top3
  -> automatic result payload + provenance
  -> Flutter customer review
       -> Top3 selection: customer_top3
       -> full catalog selection: customer_catalog
       -> cancel / no selection: Unknown remains unresolved
```

자동 inference와 사용자 resolution은 연결되지만 서로 다른 기록이다. 사용자 선택은 AI가 맞힌 결과로 재분류하지 않는다.

## 3. 측정 경계

### 3.1 100ms worker 범위

타이머는 worker가 입력 파일의 바이트를 읽기 직전에 시작한다. 다음 작업을 포함한다.

- 파일 읽기
- EXIF orientation 해석
- EXIF transpose와 RGB canonicalization
- detector resize/normalize
- RF-DETR-L inference와 box decode
- canonical box 정규화 및 stable ordering
- 모든 객체 crop 생성과 classifier preprocessing
- RepViT batch inference와 direct gate
- direct reject 객체의 조건부 DINOv3 global/local batch
- immutable fusion
- Unknown Top3 생성
- registered SKU 및 Unknown 집계
- SKU/count/location/confidence/path/provenance를 포함한 결과 payload 조립

타이머는 결과 payload가 메모리에 완성될 때 끝난다.

### 3.2 제외 범위

- 카메라 촬영
- 제품 재배치
- 재촬영
- JSON Lines IPC 왕복
- Flutter UI 렌더링
- 사용자 Top3 선택
- 상품 검색과 사용자 입력
- 결제 및 주문 저장

모델/engine load와 최초 warm-up도 100ms 표본에서 제외하지만 별도 보고한다. 상품 검색 응답시간은 별도의 UX SLA로 측정할 수 있으며 GPU worker p95에 섞지 않는다.

## 4. 현재 기준선과 한계

커밋된 `benchmarks/baselines/flutter_camera_prototype_20260729/warm_benchmark.json`의 RTX 5080 warmed CUDA 결과는 다음과 같다.

| 구간 | p50 | p95 |
| --- | ---: | ---: |
| decode/preprocess | 76.20ms | 98.68ms |
| RF-DETR-L | 99.41ms | 123.70ms |
| RepViT-M1 | 62.82ms | 80.00ms |
| 조건부 DINOv3 | 73.31ms | 90.40ms |
| postprocess | 0.34ms | 0.38ms |
| 합계 | 368.68ms | 419.20ms |

이 결과는 `cuda:0`, 3개 객체가 검출되는 단일 이미지, 20회 측정의 prototype 기준선이다. 목표까지 약 `4.2x`의 p95 개선이 필요하며 detector p95만으로도 목표를 넘는다. 객체 배치화만으로 목표 달성을 주장할 수 없다.

단일 이미지 20회 결과는 병목 탐색용 개발 증거다. E/M/H 전체 성능 또는 품질 수락 증거로 사용하지 않는다.

## 5. 보존할 canonical 자동 판정 계약

GPU 경로는 `configs/pipelines/canonical_cpu.yaml`의 의미를 바꾸지 않는다.

1. EXIF transpose를 적용한 RGB 이미지가 유일한 canonical coordinate frame이다.
2. RF-DETR-L은 `models/rfdetr_large_bakery_v1/manifest.json`의 calibrated threshold를 사용한다.
3. box는 canonical frame의 유한하고 유효한 `[x_min, y_min, x_max, y_max]`로 정규화한다.
4. 모든 candidate는 detector artifact identity, calibrated score와 provenance를 유지한다.
5. 모든 accepted detector crop에 `repvit_m1_15plus5_v1`을 실행한다.
6. immutable calibrated RepViT gate가 수락한 direct decision만 자동 확정한다.
7. direct-gate reject에만 `dinov3_vits16_15plus5_v1` global/local evidence를 실행한다.
8. fusion ranked SKU가 local Top-1과 같거나, 두 모델의 global Top-1이 ranked SKU와 같고 fusion margin이 `0.85` 이상일 때만 등록 SKU를 수락한다.
9. 나머지는 모두 `Unknown`이다. 임의 SKU로 대체하거나 자동 SKU별 합계에 넣지 않는다.
10. 모든 모델, preprocessing, calibration, prototype/support bank, policy와 engine SHA-256을 실행 전에 검증한다.

GPU 최적화는 실행 방식만 바꾼다. threshold, gate, fusion 수식, candidate order, tie-break와 `Unknown` 의미는 바꾸지 않는다. canonical CPU/FP32 composition은 reference이자 안전한 운영 경로로 남는다.

## 6. Scene presentation gate와 재촬영

재촬영은 scene이 판정에 부적합할 때만 사용한다. classification ambiguity와 분리한다.

첫 production 범위는 현재 검증된 조건으로 제한한다.

- detector 결과가 0개: scan retake `no_bread_detected`
- calibrated box-overlap IoU 이상: object retake `separate_breads`
- usable scene에서 classification이 불확실함: retake가 아니라 `Unknown + Top3`

다음 항목은 별도의 calibrated presentation-policy artifact와 locked scene-quality evidence가 생기기 전에는 추가하지 않는다.

- blur
- edge truncation
- 최소 객체 크기
- 밝기·노출
- 최소 제품 간격
- detector confidence 기반 임의 retake

검출기가 객체를 완전히 놓친 경우 detector 결과만으로 실제 누락을 항상 알 수 없다. 예상 수량, 연속 프레임 또는 scene-quality model이 필요하면 별도 설계·보정·수락 작업으로 연다.

## 7. Unknown Top3 계약

자동 판정이 수락하지 않은 객체는 다음 조건을 만족한다.

- `decision_path == "unknown_top3"`
- `sku_id == null`
- `sku_name == "Unknown"`
- Top3 길이는 정확히 3이다.
- rank는 정확히 `1, 2, 3`이다.
- SKU ID는 서로 다르고 등록 범위 `1..20`에 속한다.
- score는 유한한 `[0, 1]` 값이다.
- score 내림차순이며 동일 score는 canonical SKU order로 tie-break한다.
- registered SKU 객체는 Top3가 비어 있고 `unknown_reason`이 없다.

DINO 오류 시에도 RepViT calibrated score의 Top3와 sanitized failure provenance를 보존한다. Top3는 사용자 제안이며 자동 acceptance rule을 우회하지 않는다.

## 8. Top3 + 전체 상품 검색 사용자 확인

현재 Flutter 앱의 Top3 선택 및 전체 상품 검색 골격을 재사용한다. 새 검색 UI를 만드는 대신 inference/checkout/audit 계약을 검증한다.

| 사용자 결과 | immutable inference | audited order resolution |
| --- | --- | --- |
| 자동 결과 그대로 사용 | registered SKU | `ai_auto_customer_accepted` |
| Top3 후보 선택 | `Unknown` 유지 | `customer_top3` + candidate rank |
| 전체 catalog 검색 선택 | `Unknown` 유지 | `customer_catalog` |
| 취소·선택 실패 | `Unknown` 유지 | resolution 없음 |

원칙은 다음과 같다.

- Top3나 검색 결과는 사용자가 선택하기 전까지 최종 SKU가 아니다.
- 검색은 checkout session이 snapshot한 활성 catalog만 사용한다.
- Top3 선택은 exact candidate SKU인지 다시 검증한다.
- catalog 선택은 candidate rank를 주장하지 않는다.
- 원본 detector/classifier evidence와 provenance는 수정하지 않는다.
- 미해결 Unknown은 자동 SKU별 합계와 결제 주문에 조용히 포함되지 않는다.
- 사용자 확인 주문 결과와 자동 모델 정확도 지표를 섞지 않는다.

## 9. 검토한 GPU 접근과 선택

### 접근 A: 현재 PyTorch eager 경로만 배치화

객체별 `classifier.infer()`를 기존 `infer_many()`로 바꾸고 불필요한 PIL 반복 및 `.item()`/`.cpu()` 동기화를 줄인다. 위험이 낮고 첫 단계로 필요하지만 detector p95가 123.70ms라 단독으로 목표를 보장하지 못한다.

### 접근 B: 동일 모델·동일 판정의 정적 GPU 실행 경로

객체 배치화, tensor crop/preprocess, RF-DETR-L 및 분류 backbone TensorRT FP16, shape profile, 사전 할당 buffer, CUDA Graph를 사용한다. 민감한 score, prototype similarity, gate와 fusion은 필요하면 FP32로 유지한다. 기본 production 후보로 선택한다.

### 접근 C: FP8/INT8/FP4 또는 작은 detector

추가 가속 여지가 있지만 calibration과 품질 위험이 커진다. 접근 B의 committed receipt가 목표 미달일 때만 별도 연구로 연다. 새 calibration 및 새 locked acceptance set 없이 production에 채택하지 않는다.

## 10. 목표 GPU 구성요소

### 10.1 `CanonicalInputAdapter`

- 현재 PIL/EXIF 경로를 reference adapter로 유지한다.
- optimized adapter는 encoded bytes를 한 번 읽고 EXIF orientation을 명시적으로 해석한다.
- GPU JPEG decode를 사용할 경우 orientation을 별도로 정확하게 적용한다.
- 8개 EXIF orientation, RGB 변환, pixel/box mapping contract를 통과해야 한다.
- parity를 증명하지 못한 codec edge case는 명시적 reference adapter로 보내고 reason과 latency를 receipt에 기록한다.

### 10.2 `GpuRuntimeAdmission`

- source model, preprocessing, calibration, policy와 engine identity/hash를 검증한다.
- GPU compute capability, TensorRT/CUDA/runtime version, binding과 shape profile을 검증한다.
- benchmark에서는 fallback을 금지한다. admission 실패는 `unverified`다.
- production은 구성에 명시된 canonical CPU fallback만 허용하고 reason을 기록한다.

### 10.3 `RfDetrGpuAdapter`

- high-level `predict()` 병목을 검증된 export graph adapter로 교체한다.
- detector 입력 해상도는 source artifact/export metadata에서 읽어 engine manifest에 고정한다.
- 첫 production 후보는 static batch-1 TensorRT FP16이다.
- resize/normalize, inference, decode/NMS는 가능한 한 GPU resident로 유지한다.
- threshold, clip/order, score tie-break는 reference와 동일하다.

### 10.4 `GpuCropBatchBuilder`

- 한 이미지의 모든 detector candidate를 stable order로 모은다.
- RepViT/DINO global/local view를 GPU tensor operation으로 생성한다.
- padding은 evidence, count 또는 output object가 아니다.
- candidate를 임의 최대 개수에서 버리거나 잘라내지 않는다.

### 10.5 `RepVitGpuBatchScorer`와 `DinoGpuBatchScorer`

- RepViT는 전체 객체를 batch 처리한다.
- direct-gate reject index만 DINO packed batch로 보낸다.
- common object-count profile은 buffer 재사용과 CUDA Graph를 사용한다.
- 지원 범위 전체를 처리하는 검증된 dynamic profile을 유지한다.
- 객체 순서는 detector order로 복원한다.

### 10.6 `ImmutableDecisionAssembler`

- 기존 calibrated gate, fusion policy, margin 비교, Unknown 및 Top3 생성을 재사용한다.
- GPU adapter는 evidence를 생산하며 decision policy를 소유하지 않는다.
- host sync는 결과 payload 생성 직전으로 모으되 stable ordering을 바꾸지 않는다.

### 10.7 `LatencyRecorder`

- end-to-end gate는 host monotonic clock으로 측정한다.
- GPU stage 진단은 CUDA Event와 NVTX range를 사용한다.
- stage마다 `torch.cuda.synchronize()`를 호출해 pipeline을 직렬화하지 않는다.
- stage p95 합을 total p95로 사용하지 않고 표본별 total을 집계한다.

## 11. 정밀도와 parity 단계

1. **Batch FP32:** 현재 모델/preprocessing을 유지하고 객체 batch 및 sync 제거 효과를 측정한다.
2. **Tensor preprocess FP32:** PIL 다중 crop을 GPU tensor path로 바꾸고 canonical/crop parity를 검증한다.
3. **TensorRT FP16 detector:** RF-DETR-L을 FP16으로 실행하고 score decode/threshold 경계는 필요하면 FP32로 유지한다.
4. **TensorRT FP16 classifiers:** RepViT/DINO feature extraction은 FP16, prototype/gate/fusion 입력은 민감도에 따라 FP32로 유지한다.
5. **CUDA Graph/buffer reuse:** 수치 경로와 shape가 검증된 뒤 적용한다.

각 단계는 직전 단계와 독립된 benchmark/quality receipt를 만든다. FP16에서 final decision parity가 깨지면 mixed precision으로 원인을 격리한다. parity를 복구하지 못하면 새로운 calibrated backend로 취급하고 개발/보정/새 locked acceptance evidence를 분리한다.

| 파일 읽기 + canonical decode/EXIF/RGB | 12ms |

## 13. 성능 측정 프로토콜

### 13.1 실행 조건

- 모델, engine, calibration, policy, preprocessing, data manifest, seed와 code commit을 고정한다.
- 고정 E/M/H performance manifest를 사용하고 그룹별 최소 100개 유효 관측치를 만든다.
- 최소 20회 warm-up 후 측정하며 warm-up은 통계에서 제외한다.
- reference/candidate 실행 순서를 교차해 cache/order 편향을 줄인다.
- candidate와 reference를 동시에 GPU에서 실행하지 않는다.
- GPU power/clock/온도/전력, driver, CUDA, cuDNN, TensorRT, PyTorch와 background process를 기록한다.
- engine build는 측정 밖에서 수행하고 build/load/warm-up 시간을 별도 보고한다.

### 13.2 필수 보고값

- 전체와 E/M/H별 p50, p90, p95, p99, max, sample count
- decode, detector, crop, RepViT, DINO, fusion/Top3/payload stage 통계
- 이미지별 object 수와 conditional DINO object 수/비율
- selected shape profile, runtime mode, fallback 여부/reason
- CPU/GPU memory peak, engine load와 warm-up 시간
- reference 대비 absolute latency와 speedup

### 13.3 성능 수락 조건

- E p95 `<=100ms`
- M p95 `<=100ms`
- H p95 `<=100ms`
- 전체 p95 `<=100ms`
- verified GPU path sample 100%
- silent fallback 0건
- committed performance receipt 없이는 속도 개선을 주장하지 않음

## 14. 품질 및 사용자 보조 평가

성능 개발 데이터, calibration 데이터와 locked acceptance 데이터는 분리한다. locked 결과가 precision/profile/구현 선택에 영향을 주면 새 locked set에서 다시 검증한다.

canonical frame IoU `0.50` deterministic one-to-one matching으로 다음을 보고한다.

- SKU error, miss, duplicate, non-target, split, merge
- registered SKU 및 Unknown final-versus-ground-truth count
- direct, DINO-local, global-consensus, Unknown decision path 분포
- detector box/score, RepViT gate, DINO global/local, fusion rank/margin 경계 사례
- Unknown Top1/Top3 correct count와 recall
- Top3 miss 목록
- Top3 선택률, catalog 검색 전환율, 검색 성공률
- candidate rank별 사용자 선택과 사용자 취소/오선택률

production 수락 조건은 다음과 같다.

- 새 잘못된 자동 등록 SKU 0건
- 새 miss/duplicate/non-target/split/merge 0건
- reference에서 정확했던 객체가 다른 등록 SKU로 변하지 않음
- ambiguity는 임의 SKU가 아니라 Unknown
- Unknown은 자동 SKU별 합계에서 제외
- 최신 committed canonical reference floor 유지
- 기존 floor `Top-1 >=1349/1406`, `Top-3 >=1390/1406`, `FP=0`, `FN<=5`, `Unknown<=48`, `A-to-B<=4`보다 낮은 floor 선택 금지
- 실행 시 더 최신이고 엄격한 canonical receipt가 있으면 그 receipt/hash 사용
- 새 locked set에서 Unknown Top3 recall 100% 목표
- Top3에 정답이 없으면 catalog 검색으로 이동하고 강제 선택 금지
- SKU/count/location/confidence/path/provenance 일치

Top3 recall 100%는 locked set 목표이며 모든 미래 입력에 대한 보장이 아니다.

## 15. Artifact 및 provenance

ONNX/TensorRT engine은 대용량 외부 artifact로 취급한다. Git에는 payload를 넣지 않고 작은 manifest, lock entry, build recipe와 compact receipt만 둔다.

각 engine manifest에는 최소한 다음이 포함된다.

- engine ID, byte size, SHA-256, storage class, expected local path
- source model/checkpoint ID와 SHA-256
- exporter code commit, export recipe, opset와 exporter/runtime versions
- preprocessing ID/hash와 input color/order/layout/range
- shape profile과 detector resolution 출처
- precision, layer override, calibration ID/hash(해당 시)
- input/output binding name, dtype, shape, semantic meaning
- TensorRT/CUDA/cuDNN version와 GPU compute capability
- build environment와 build receipt hash

결과 payload는 기존 model/calibration/policy provenance에 engine/profile/runtime identity를 추가한다. 재현 정보가 부족하면 실행을 거부한다.

## 16. 테스트 전략

### 16.1 단위/contract

- 8개 EXIF orientation, RGB 변환, canonical pixel/box mapping
- finite/in-bounds box normalization과 stable order/tie-break
- 다양한 object 수의 GPU crop/reference crop parity
- batch packing/unpacking 후 object order/path 보존
- direct reject에만 DINO 실행
- local Top-1/global consensus/margin `0.85` 경계
- Unknown 정확히 Top3와 registered empty Top3
- registered/Unknown 합계 불변식
- Top3 exact candidate 선택과 catalog 선택 audit 분리
- engine binding, artifact hash, runtime admission
- benchmark fallback 금지와 receipt schema

### 16.2 통합/GPU

- reference FP32와 각 최적화 단계 raw evidence/final decision 비교
- 실제 RTX 5080 engine load, warm-up, shape profile, CUDA Graph replay
- mixed object count와 conditional DINO
- missing/corrupt engine, hash mismatch, unsupported runtime fail-closed
- no-object/overlap retake에서 Top3 미노출
- usable-scene Unknown에서 Top3 + catalog search 연결
- canonical CPU와 `portable_cpu_smoke/` 무변경 회귀

### 16.3 성능/locked acceptance

- 고정 E/M/H latency suite와 전체 manifest suite
- 새 locked quality suite의 IoU 0.50 평가
- skipped/artifact 부재 suite는 `unverified`이며 passed가 아님

## 17. 단계별 전달

1. **Benchmark 신뢰성:** 측정 경계, E/M/H manifest, receipt schema를 고정한다.
2. **Batch FP32:** camera runtime의 object별 `infer()`를 `infer_many()`로 교체한다.
3. **Presentation 연결 검증:** usable Unknown은 기존 Top3+검색, no-object/overlap은 retake인지 검증한다.
4. **Tensor crop/preprocess:** canonical/crop parity를 확보한다.
5. **RF-DETR TensorRT FP16:** detector adapter/engine/admission을 추가한다.
6. **RepViT/DINO TensorRT FP16:** conditional packed batch와 mixed precision을 추가한다.
7. **CUDA Graph/buffer reuse:** 검증된 shape에만 적용한다.
8. **수락:** performance와 새 locked quality receipt가 모두 통과한 후보만 production opt-in으로 올린다.
9. **조건부 연구:** 100ms 미달 시에만 FP8/INT8/FP4 또는 detector 교체를 별도 설계한다.

각 단계는 실패 테스트를 먼저 식별하고 가장 작은 producer/consumer surface를 함께 변경한다. 품질 gate가 깨지면 다음 최적화를 쌓지 않고 원인을 해결하거나 되돌린다.

## 18. 운영 모드와 롤백

- `cpu_canonical_fp32`: 현재 canonical/reference
- `gpu_reference_fp32`: 수치 비교용 GPU reference
- `gpu_batch_fp32`: batch/sync 최적화
- `gpu_trt_fp16`: production 후보
- `gpu_quantized_experimental`: 별도 보정 전 production 금지

기본 canonical CPU config를 GPU로 조용히 바꾸지 않는다. GPU는 opt-in이고 receipt가 지정한 환경/artifact에만 admission된다. 이상 시 last-known-validated mode로 명시적 롤백하고 reason과 runtime mode를 기록한다.

## 19. 범위 밖

- Top5
- 새 catalog 검색 UI 재설계
- 사용자 선택 시간을 100ms GPU gate에 포함
- 검증되지 않은 blur/edge/size retake heuristic
- canonical CPU 모델 또는 판정 정책 교체
- 새 SKU 학습이나 label policy 변경
- 정확도 증거 없는 quantization/작은 detector production 채택
- `portable_cpu_smoke/` 또는 legacy GPU 경로 삭제·이동·행동 변경
- private/proprietary dataset, checkpoint, engine payload의 Git 커밋

## 20. 완료 조건

1. 자동 pipeline, scene gate, Unknown Top3와 사용자 resolution 경계가 구현/검증된다.
2. 모든 artifact/runtime admission이 hash와 compatibility를 검증한다.
3. RTX 5080에서 E/M/H 및 전체 warmed worker p95가 각각 100ms 이하인 committed receipt가 있다.
4. 새 locked set의 quality gate가 통과하고 오류/Unknown/Top3/count/path/provenance 보고가 완전하다.
5. Top3와 catalog 선택이 immutable inference를 수정하지 않는 별도 audit path로 남는다.
6. configs, docs, runtime payload와 compact benchmark summary가 실제 동작과 일치한다.
7. 필수 suite가 unavailable/skipped이면 완료가 아니라 `unverified`다.
